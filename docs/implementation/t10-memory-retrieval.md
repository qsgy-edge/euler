# T10: scoped memory retrieval (synthetic)

Core retrieval is available through `ProbeStore.searchMemories` and the normal `AgentRun` `memory.search` tool. Validation uses disposable SQLite and synthetic archive inputs. Retrieval receipts use existing JSON ledger fields without changing the disposable schema or migrating real data. [#10](https://github.com/qsgy-edge/euler/issues/10) · [#64](https://github.com/qsgy-edge/euler/issues/64) · [#69](https://github.com/qsgy-edge/euler/issues/69)

`ProbeStore.searchMemories(activity, request)` defaults to the bound local project plus applicable workspace/personal memory. `noActiveProject: true` removes that default; it never grants another project. A trusted synthetic Host must archive a separate `user`-role `memory-discovery-approval@1` decision binding the active intent/goal event, exact registered project IDs, target environments and cumulative result/byte budgets. `authorizeMemoryDiscovery` re-reads the durable source and its Host-reported role, rejecting `assistant`/`tool`/unknown roles and mismatched arguments. Each intent admits **one** grant: replaying the same decision returns its original grant and counters, while a different decision cannot reset its budget or change its scope. A fixed additional query allowance of `min(128, max(8, maxResults * 4))` is durable and charges even empty or dirty searches. The grant is rechecked on every query; completion revokes it transactionally and permanently blocks new discovery for that intent, even if its status later returns to active. Explicit owner revocation works while paused. Query-supplied target metadata cannot override a cross-project target fixed by the grant. No operation or guidance scope changes.

Search checks projection/current-head agreement (including canonical source project and scope before any FTS match) and FTS external-content integrity, then queries bounded FTS candidates and replays their canonical event, revision, verification evidence and source. Latin/digits use NFKC lowercase; Han runs add overlapping bigrams in the projection (`latin-cjk@3`), with script boundaries and canonical text preserved. Numeric query terms must match exactly and, when adjacent to a Latin identifier in the query, must remain adjacent to that identifier in the candidate (for example, `RFC 42` cannot admit `RFC 43 ... phase 42`); separate numeric questions need separate searches. Default FTS returns `unsupported-query` for a one-Han-character query. Single-digit exact terms remain supported. Applicability grammar is checked at capture and rechecked fail-closed on read; legacy bare agent/platform tokens remain accepted. No vectors, router/reranker LLM or fixed-result padding.

Ranking uses a fresh in-memory SQLite FTS5 corpus containing only the qualified normal/reference-only lexical candidates, bounded by the existing 256-candidate limit. Each distinct literal query group forms a lane. SQLite `bm25()` supplies its actual score with k1=1.2 and b=0.75; statistics never include ungranted, inapplicable or status-only records. This is BM25 over the eligible lexical candidate corpus, not the entire memory collection. A single populated lane uses BM25 order; multiple populated lanes use reciprocal-rank fusion with k=60. Ties use the best lane position, first matching query-lane ordinal, then stable canonical insertion order. The result `rank` is the ascending SQLite score or the negative RRF score. Current-claim/target-environment/effective-validity dedup occurs after ranking, preserving the best candidate; equivalent applicability spellings share a key. Status markers have `rank: null`, do not affect fact statistics, and follow facts in query-lane/canonical order. Cursor version 2 binds the ranking/tokenizer versions, qualified corpus identities and final candidate heads/order. See [SQLite's BM25 contract](https://www.sqlite.org/fts5.html#the_bm25_function).

Shared-scope records are evaluated for each authorized target project. Results carry `projectId` as source provenance, `targetProjectId` as the analyzed project, plus source, version and target labels; one record may occupy separate target pages. Unknown cross-project targets are `reference_only`; expired/conflicted/stale states return only a bounded status with a claim digest. Dirty/unavailable responses never imply absence. Oversized candidates are skipped with an explicit partial-coverage reason; `complete: false` means the result is not a full-history analysis. Rebuild removes projected rows by canonical record identity even if their owner/scope projection is corrupt. The integrity check currently runs per query in the disposable probe; production performance and a cheaper guarded watermark require a measured workload.

## Explicit single-Han search

In a `session`, `/memory-han 榆` reads the first memory page and `/source-search-han 榆` reads the first published project source page. Model tool calls and their continuations use the same mode and query:

```text
memory.search {"query":"榆","mode":"single-han"}
source.search {"query":"榆","scope":"project","mode":"single-han"}
```

The mode requires one Han code point after trimming and NFKC normalization. It checks projection health and takes at most 256 scoped projection rows for literal matching. If a 257th row exists, the page is `unavailable` with `single-han-scan-limit` and no cursor. A successful memory search orders matches by canonical insertion order before the usual deduplication and paging. Source matches follow the existing published projection order. Scope, current-head and applicability checks, source authority, task and byte budgets, and cursor binding apply. Published-source search has access only to approved units and inert proposals. A tool caller can resume a returned `nextCursor` by supplying it as `cursor` with the same query, mode and scope.

Literal memory receipts record `single-han-literal@1`, `eligible-literal-order@1` and `scoreKind: literal-order`. They carry no BM25 or RRF scores. The normal FTS path keeps its existing ranking and cursor contract. X-02 independently measures single-Han coverage and non-single-Han ranking before any decision to change the default.

## Retrieval and delivery receipts

Completed lexical queries return `SearchPage.retrieval` (`memory-retrieval@1`) to the Host: query/lane hashes, query tokenizer `latin-cjk-query@1`, index tokenizer `unicode61+latin-cjk@3`, SQLite/ranking versions, corpus identity, actual per-lane BM25/position and fused scores, immutable candidate identities, returned order and duplicate/page/byte-budget decisions. A trace candidate's `scoreKind: rrf` carries the positive reciprocal-rank sum; the result's negative `rank` is only its ascending sort key. Gates that stop before the lexical query retain their explicit coverage reason and do not invent evaluated candidates. Raw query text remains in its existing tool-arguments archive.

Each candidate measurement counts the UTF-8 JSON bytes of that search-result object and records the existing conservative budget charge in separate `budgetUnits`. It is not a provider-token measurement or an allocated share of final transport overhead. The model tokenizer and actual tokens are unavailable/unsupported; candidate cost and currency are unknown. Neither byte counts nor whole-attempt usage are presented as per-candidate tokens or charges.

`AgentRun` removes the trace before creating `modelResult`. Only Core can attach `memory-retrieval-tool@1` metadata to the existing tool-result ledger event, binding the exact returned `modelResult` hash. An assembly adds `memory-delivery@1` to the corresponding existing `selection` entry only when that archived tool source is actually selected. This captures returned identities/order/measurements and participates in the assembly identity and Store admission checks. A completed query cancelled before the next assembly has a returned receipt and no delivery selection. `usedMemories` retains ownership of current-head eligibility. Receipts remain outside model data; restart, backup and the existing JSON-aware purge dependency closure include these fields. Purging an examined but omitted candidate also removes its retained query trace while preserving unrelated canonical memories.

## Evidence Boundary

The tests exercise Core retrieval with a registered synthetic session. `noActiveProject` proves that an absent *active retrieval project* gives no implicit results and does not prevent an explicit grant; it does not prove a production Host can create a session with no provenance project binding. The archive proves the typed approval bytes, task identity and Host-reported `user` role, but not that a real Host authenticated and presented a decision to the owner; owner-channel validation, approval UI and real-loop admission remain T18 integration evidence. The committed held-out corpus covers lexical judgments only; lifecycle and cross-project cases are frozen development judgments, and Git history alone cannot prove held-out gold was sealed before the first result (session transcript records the initial digest). Current Store has no public transition that makes an active record `stale`, so that status branch is implemented but not independently exercised via the public seam. Full-history coverage and downstream source.expand are not claimed as validated by this slice. A projection mismatch or missing FTS posting returns dirty/unavailable and can be rebuilt; a positive match is always revalidated against canonical owner evidence.
