## 4. 在 Euler 上层评估中的职责建议

| 职责 | 评估对象与问题 | 评估后的动作边界 |
| --- | --- | --- |
| 运行中评估与纠偏 | 当前任务是否有效推进，诊断是否停滞，是否需要独立复核 | Runtime 按既有授权暂停相关重复修改、诊断、恢复或切换通道 |
| 行为自进化评估 | 候选代码、Skill、提示词或持久策略是否改善未来任务 | 对应 artifact owner 在规定验证和批准完成后发布、拒绝或回滚 |
| 候选工作区，LayerFS 可作为后端 | 候选使用了哪些文件，如何冻结、分叉、比较和丢弃 | 提供状态与快照；不判断行为改善，不授予执行或发布权限 |

两类评估可以复用真实结果、source 引用/hash、验收表达和独立复核基础设施，不预建统一评分器、第二套任务真值或万能自进化引擎。不同对象仍保留不同的验收、状态 owner 和发布门槛。

例如，本轮按已有规则切换到获准的备用模型属于运行恢复；从失败中提出永久修改路由策略或 Skill 的建议，才进入行为自进化候选。评估器给出判断，Runtime 或制品 owner 执行动作；评估器不能直接改权限、长期策略或活动代码。

## 5. 待设计的最小机制

以下是候选方案，不是已经批准的实现契约。

### 5.1 按任务证据判断进展

从既有 intent、工具事件和产物自动累积有界状态：当前验收条件、执行阶段、失败特征、被测源码/产物身份、最近一次产生的区分性证据。不要求用户手工维护链路，也不每轮重读整段会话。

至少区分工具调用成功、子进程结束、分项断言通过、任务条件满足。读取成功、新增代码、编译通过和模型自述不能清除尚未解决的行为失败；但如果目标本来就是编译验证，则编译通过是有效进展。

Hash 或加载产物不匹配表示实验无效。事实采集需要来自 Host 的实际执行结果；任意 stdout 中的 pass、JSON 或模型提供的“回执”都不能自动成为权威验收。验收条件本身也可能写错，必要时独立检查探针和正反对照。

### 5.2 组合触发，保留跨轮失败历史

候选触发条件：同一验收经过两次针对性修复仍无新证据；修改未触及失败路径；已稳定内容反复被破坏；实验身份不一致；准备从局部失败推出必须换引擎或重写架构等高影响结论。

“两次”只是待校准初值。触发动作优先为暂停同一路径的重复修改、转入诊断，不能等同于宣布模型降智或停止整个任务。正常的新需求、预期取消和能够排除假设的失败实验不应被等量计数。

同一目标下的“继续”、压缩、换窗和 reasoning effort 变化不自动清除失败历史。若 owner 继续建立关联的新 run，仍遵守现有 run/预算语义；保留问题历史不意味着绕过已耗尽预算或重新执行 unknown 操作。

### 5.3 独立诊断与受控升级

诊断者获得原始目标、关键事件和冻结产物引用，自行取证；主模型的根因解释作为待检验假设。上下文独立和模型/服务通道独立分别考量，同一供应商的两个别名不能自动算独立后端。

独立诊断优先检查：测试是否实际运行了新代码、失败属于哪个阶段、探针是否制造了错误、控制变量是否足以排除解释。审阅超时、失败或证据不足明确保留状态，不按通过处理。

自动升级必须受预先批准的模型/通道、数据范围和预算约束。没有可用获准通道时给出一次具体告警与下一步，而非无限重试或静默扩权。升级不改变原验收标准，不删除失败记录，不直接修改持久配置。

### 5.4 通道质量观察

任务停滞先触发诊断；供应商降级或能力不匹配属于后续归因。可在异常时运行有客观答案/可执行检查的小型合成探针，之后按实际需要增加低频抽样，比较当前通道历史与可信参考通道。

名义模型、reasoning effort、响应速度、思考 token 数及供应商自报字段仅作受限辅助数据，不能证明实际身份或质量。探针通过不代表能完成当前复杂任务；两个通道都失败应检查任务、上下文和环境。一次告警不自动形成长期“该模型不可用”的事实记忆。

## 6. 旧账号不可用时的验证方案

| 验证方式 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 历史记录按时间给检测器，隐藏后续答案与用户提醒 | 当时已有的证据是否足以触发诊断，以及触发水位 | 旧后端现在会如何响应、自动切换当时一定能解决任务 |
| 受控故障样例 | 工具成功位包着 exit255、陈旧 DLL、错误位置未覆盖、虚假 pass、通道异常等路径能否正确处理 | 合成故障覆盖了真实降智的全部分布 |
| 正常行为对照与未参与调整的样例 | 对新增需求、预期失败和有效调试的误报情况，是否对旧案例过拟合 | 全部任务上的普遍可靠性 |
| 新任务中的观察或获准试运行 | 实际减少的无效尝试、诊断效果、误报与额外成本 | 补回旧供应商变更的因果证明 |

历史回放不重新执行旧工具，也不调用旧账号。首次可判定触发即可停止；一旦模拟动作偏离历史轨迹，后续旧结果不能冒充新动作产生的结果。若需查看某 checkpoint 的源码，应使用当时版本；缺少快照时报告缺口，不能拿最新代码泄露后续答案。

LayerFS 文件快照同样不能恢复远端模型、账号、网络服务和当时供应商状态。完整旧任务复现不是本机制的必要前置。

建议的检查重点：到 L711 已能触发诊断；工具成功但子进程失败、分项 pass 但超时均不被当成完成；正常反例不被统一判为降智；保持名义型号不变的受控响应劣化能进入复核；暂停、诊断和获准切换的每一步都有真实结果。

“到 L711”是本案例的候选回归检查点，尚未运行检测器，不能写成已通过。整体效果还需测误报、漏报、触发前无效修改次数和额外 token/延迟；等待用户的时间不能算无效执行时间。结构化失败可由代码检查，语义充分性仍需独立判断，不能承诺穷尽识别。

## 7. 后续实施仍需决定的事项

- 在届时 Euler Runtime 中选择最小切片与接入边界；不提前改变现行规格、实施票依赖或首次交付范围。
- Host 如何提供真实子进程/测试结果及实际加载产物身份；不能仅依赖工具 `isError` 或任意日志文本。
- 进展状态的最小字段、归属、恢复与生命周期；优先复用 intent、source/archive 和调用账本，不预建通用框架。
- 诊断触发阈值、检查频率，以及触发后暂停哪些动作。
- 获准的诊断/升级通道、数据范围、成本预算、不可用时的处理和恢复条件。
- 离线正反例、独立样例和新任务评估方式。先读取被分析会话的后续进展，再决定哪些历史错误仍有代表性。

初步实现建议为“真实结果采集 → 有界停滞检测 → 独立诊断和受控升级”；通道探针按验证需求加入。此顺序是建议，尚未形成实施授权。
