## 结论先行

### Blocker

- **[confirmed] 不能直接把 Pi Harness 或 DSH 当前 agent loop 当作 Q6 execution ledger。** Pi 的 `AgentHarness.create()` 在已有 record 时走 `HarnessNotImplemented("create.restore")`，`prompt`、`resume`、hooks、events 以及主要操作路径仍返回 `HarnessNotImplemented`（Pi `pi-agent-core/dist/harness/agent-harness.js:44-165`）。DSH 当前 agent loop 有 Session 事件和恢复机制，但没有每次真实 model transport attempt 的 `started/finished` core receipt（DSH `packages/core/agent-loop/src/agent.ts:339-405,496-541`；`packages/core/session/src/known-event-types.ts:18-70`）。

### High

- **[confirmed] 采用 explicit hybrid。** 运行时使用 Pi 已能运行的 `Agent`/`AgentSession`、context conversion、compaction 与 tool loop；Q6 的 ledger 由 Host/Harness 核心自有并单独写入。DSH 只提供 typed append-only log、连续序号、surface projection、flush 与冷恢复/repair 的实现参照。
- **[confirmed] Pi 普通 Session persistence 不是首次发送前 durable barrier。** 新 session 将 `flushed` 置为 false；没有 assistant entry 时 `_persist()` 只保留内存状态，首次 assistant 到达后才批量创建 session 文件（Pi `dist/core/session-manager.js:645-665,724-759`）。因此不能用 Pi Session 文件证明首个 request receipt 已在发送前落盘。
- **[confirmed] DSH 的 generic checkpoint 不是 attempt receipt。** DSH 会在 `llm/stream` 下游 adapter 调用前 flush request prefix，失败时 fail-closed（`packages/session/session-checkpoint-policy/src/index.ts:20-37,52-82`）；但 agent 只写 `request/header`、`request/context` 后调用 stream（`packages/core/agent-loop/src/agent.ts:339-405,496-541`），`llm/retry` 记录的是 retry 调度/等待，不是每个网络 attempt 的开始和结束（`packages/llm/llm-retry/src/index.ts:126-153`）。

### Medium

- **[confirmed] DSH 的冷恢复边界必须显式保留。** `load()` 可对未闭合 turn 生成 closers 并通过 `commitRepair()` 持久化；`inspect()` 只在内存中提供视图，不提交修复；live open turn 在 flush 后仍拒绝作为冷 snapshot 加载（`packages/session/session-persistence/src/coordinator.ts:779-796,972-1029,1055-1065`；`packages/session/session-persistence/src/index.ts:201-231`；`packages/core/session/src/repair.ts:18-132`）。
- **[confirmed] DSH append 与 durable flush 是两层。** `Session.append()` 先同步进入内存 canonical log，observer 由异步 persistence 处理；`flush()` 才等待 durability callbacks（`packages/core/session/src/index.ts:568-600,1020-1037`）。其 backend 的连续批次写入返回时才算 durable，crash repair 明确允许 truncate 与 append closers 分两步（`packages/session/session-persistence/src/coordinator.ts:181-196,686-733`）。
- **[inference] Q6 的“模型不可修改”必须是 capability/writer 约束。** DSH 的 `SessionEventMap` 本身是 merge-extensible，且只有 surface event type 才允许携带 `surfaceOp`；Q6 需要把 receipt writer 留在核心，并测试 receipt 不会进入 model surface/provider payload（DSH `packages/core/session/src/types.ts:215-219,330-339`；`packages/core/session/src/index.ts:625-632`）。

### Low

- None.

## 采用边界

| 层 | Q6 采用 | 不直接采用 | 理由 |
|---|---|---|---|
| Agent runtime | Pi 稳定的 `Agent`/`AgentSession`、context/tool/compaction loop | Pi `AgentHarness` v2 scaffold 作为生产执行入口 | 稳定 loop 可运行；Harness 的 restore 与操作方法仍是桩 |
| Canonical ledger | 自有 Host-owned typed append-only ledger | Pi 普通 SessionManager 作为 receipt 存储；DSH 当前 agent loop 作为完整 attempt 语义 | 两者都缺少 Q6 所需的完整发送尝试状态边界 |
| Storage primitive | 借 DSH 的连续 seq、不可变事件快照、批量 durable flush、torn-tail/未闭合边界恢复 | 直接复制 DSH 的全部 SessionEventMap 或插件总线 | 只借已验证的持久化原语，避免把领域事件和运行时耦合搬过来 |
| Projection | model surface 与 log-only receipt 分离；未来 Trajectory/metrics/audit 只读 | 把 Q6 做成 Trajectory UI | Trajectory 是消费者/投影，不是执行真相源 |
| Transport boundary | 在最终 adapter/transport boundary 生成 attempt receipt | 由 header、chunk、retry 或 telemetry 推断 attempt 状态 | 只有最终边界知道冻结后的真实 payload 与实际网络调用 |

## Q6 最小协议

1. Context Orchestrator 生成不可变 `context/assembly@v1`，记录 intent/project/policy/cache epoch、retrieval/selection/order/ref/hash、P0-P3 预算、reserve/margin/degradation 与 assembled-context hash。
2. 先 append 并 flush assembly。预算不满足、取消或该 barrier 失败时禁止网络发送。
3. 所有允许的 middleware 与 adapter 处理完成后冻结 canonical transport payload，生成 `attempt_id`、`attempt_ordinal`、最终 route/provider/model、payload hash、encoding/hash algorithm 与 adapter version；append 并 flush `model/request-attempt-started@v1`。
4. started barrier 成功后才调用网络。网络返回、失败、取消或进程正常收尾后写 `model/request-attempt-finished@v1`，将未知字段保持为 unknown，不用估算冒充事实。
5. `assembly/no-started` 解释为 `not-dispatched`；`started/no-finished` 必须解释为 `orphaned/unknown-sent`，不得推断为“未发送”。只有 provider 幂等键/查询等外部证据能进一步消歧。
6. receipt 是 log-only core event，类型上禁止 `surfaceOp`；model surface projector 与 provider payload builder 都必须排除 receipt。writer 只在核心 capability 内可调用，模型、memory/source、plugin 或远端返回内容不能写 receipt。

两个 dispatch 前 barrier 有序但不要求彼此原子：

```text
assembly append + flush
  -> freeze final transport payload
  -> started append + flush
  -> network
  -> finished append + flush
```

## 证据分级

### 已证实

- Pi 两个已安装包均为 `0.84.3`（各自 `package.json:2-4`）。
- Pi 稳定 `AgentSession._runAgentPrompt()` 调用 `this.agent.prompt()` 并在需要时继续 `agent.continue()`（`pi-coding-agent/dist/core/agent-session.js:747-758`）；底层 agent loop 在 `transformContext`、`convertToLlm` 后直接调用 `streamFunction`（`pi-agent-core/dist/agent-loop.js:178-195`）。这些是可复用的运行时能力，不是 Q6 receipt durability 证明。
- Pi Harness session 类型已经设计了 `operation_started`、`operation_finished`、`step_attempt`、`tool_started` 与 `findOpenOperations` 等记录/恢复形状（`pi-agent-core/dist/harness/session/types.d.ts:65-179,204-210,291-293`），状态 reducer 强制连续 seq 并维护 open operations（`pi-agent-core/dist/harness/session/state.js:29-116,212-214`）；但 Harness 执行路径仍未实现。
- DSH canonical log 明确是 append-only、连续 seq，message history 从 log 派生；`request/header` 与 `request/context` 是 log-only request metadata（`packages/core/session/src/types.ts:215-219,287-301`）。
- DSH `known-event-types` 当前核心目录包含 `request/header`、`request/context`、`assistant/chunk`、`llm/retry` 等，但没有 `model/request-attempt-started/finished` 这类逐次 transport receipt（`packages/core/session/src/known-event-types.ts:18-70`）。
- DSH 的 repair 逻辑能区分 tool 未开始与已记录但无结果的 unknown outcome，证明其恢复判读方法可借鉴；Q6 需要把同一谨慎语义应用到 model attempt（`packages/core/session/src/repair.ts:12-16,89-123`）。

### 推断

- 最小且可维护的目标是 Pi runtime + 自有 ledger，而不是在 Pi 与 DSH 之间选择整套系统。
- Q6 ledger 应只借 DSH 的存储/投影/恢复原语，并在最终 transport boundary 补齐 assembly 与 per-attempt 状态；Pi Harness 的 record schema 可作为形状参考，但不能当作现成实现。
- 只要 receipt writer 在核心，且 projection exclusion 有自动测试，Q6 可以保持模型不可修改和 receipt 不污染 prompt 的边界。

### 未证实

- 未运行 Pi 或 DSH 真实 agent loop，未做进程崩溃、网络中断、retry、发送前失败、started 后崩溃的 fault-injection。
- 未实现 Q6 精确 schema、存储后端、迁移和自动测试；不能把本报告写成实现已通过。
- 没有用户实际 crash log，无法判定历史故障的具体根因。
- 已安装包、固定检出和未来运行环境不等价；本结论只覆盖上面列出的本地版本。
